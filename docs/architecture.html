jcli architecture

jcli is a small Rust CLI that reads Jira Cloud for coding agents. It prints an issue as Markdown, searches issues with JQL, downloads an issue's attachments and lists the test runs Xray Cloud stores for a test issue. It never changes data in Jira or Xray. The binary is built with the stable toolchain and blocking reqwest, without an async runtime (ADR 0002).

Commands

CommandOutput on stdout
jcli issue read <KEY>The issue as Markdown
jcli issue search --jql <JQL> --json [--limit N]The first page of matching issues as JSON
jcli issue attachments <KEY> [--out DIR]A Markdown list of the downloaded files
jcli xray test-runs <KEY> --json [--status S]... [--sort started-on] [--direction asc|desc]The first page of the test issue's test runs as JSON
jcli whoamiThe account the credentials belong to, on one line

<KEY> is a canonical issue key such as ABC-123: a project part of 2 to 10 uppercase ASCII letters or digits that starts with a letter, a hyphen, and a positive number without leading zeros. URLs and bare numbers are rejected.

Runtime flow

src/main.rs declares the commands with clap's derive API and hands each one to a function in src/commands.rs. Clap rejects unknown commands, missing required flags and out-of-range values such as --limit 0 before jcli reads any configuration, and exits with code 2.

Each function in src/commands.rs is the application service for one command. It runs the same steps in order:

  1. Parse the issue key, if the command takes one. A malformed key exits 1 before jcli loads configuration.
  2. Load the configuration. xray test-runs also loads the Xray configuration before it sends any request, so a missing Xray setting fails without network traffic.
  3. Build the client and send the requests.
  4. Render the complete result and write it to stdout in one call, then exit 0.

Every function ends the process itself and returns !. A failure at any step prints error: <message> on stderr and exits with the step's code. stdout stays empty on failure.

Exit codeCause
0Success
1Invalid issue key
2Configuration error, or a usage error reported by clap
3Jira or Xray request failure, or a Jira response jcli refuses to use
4Filesystem failure, unsupported platform for attachments, or a failed stdout write

xray test-runs resolves the issue key to Jira's numeric issue ID with one Jira request, then calls Xray. issue attachments checks for Unix before it loads the configuration and exits 4 on other platforms.

Modules and dependencies

jcli has one bounded context: reading Jira issues and their Xray test runs for an agent. The ubiquitous language uses Jira's terms: issue, issue key, attachment, JQL, test issue and test run.

  • src/main.rs: the clap command tree and dispatch.
  • src/commands.rs: the application services, one function per command, plus exit handling. It wires all other modules together.
  • src/issue_key.rs: IssueKey, a value object that only exists in canonical form. Its parse error never echoes the input.
  • src/config.rs: Config for Jira and XrayConfig for Xray, resolved from the process environment, the .env in the working directory and the per-user config.toml. It owns SanitizedUrl, which the Debug output of configuration and clients uses.
  • src/jira/: the Jira side of the anti-corruption layer. client.rs is the GET-only HTTP client with status mapping, body limits and JQL error redaction. issue.rs, attachment.rs and search.rs are serde models that deserialize only the fields jcli requests. Jira's names such as issuetype and isLast stop at their serde attributes.
  • src/xray/: the Xray side. client.rs exchanges the API key for a bearer token and runs the getTestRuns GraphQL query. test_runs.rs holds the response models, the page sort and the TestRunsOutput JSON contract.
  • src/adf/: translates Jira's Atlassian Document Format (ADF) into Markdown and renders the issue page for issue read (ADR 0008).
  • src/issue_search.rs: maps a Jira search page to the IssueSearchOutput JSON contract.
  • src/attachments.rs: plans and checks attachment downloads, builds safe file names, and streams and writes each file (ADR 0009).
  • src/output.rs: shared output rules: escaped pretty JSON and single-line, control-free terminal fields.

There is no separate domain model between the Jira response and the output. The serde models in src/jira/ and src/xray/ hold only the requested fields, and adf, issue_search and xray::test_runs turn them straight into the output contract. That translation is where Jira and Xray shapes end.

Arrows show the imports that exist between modules.

config, issue_key and output import no other jcli module. The Jira and Xray clients do not know about each other; only commands combines them. All modules are private to the binary crate, and Rust's module privacy is the only boundary check (ADR 0004).

Configuration

jcli reads six settings. The Jira settings are required by every command, the Xray settings only by xray test-runs.

Environment variableconfig.toml key
JIRA_BASE_URLbase_url
JIRA_EMAILemail
JIRA_API_TOKENapi_token
XRAY_BASE_URLxray_base_url
XRAY_CLIENT_IDxray_client_id
XRAY_CLIENT_SECRETxray_client_secret

Precedence is per setting: the process environment, then the .env file in the current working directory, then the per-user config.toml (ADR 0006).

  • The .env is read from the working directory only, with no search in parent directories. jcli parses it with dotenvy without changing the process environment. A leading UTF-8 byte order mark is skipped, and a duplicate key keeps its first value.
  • The TOML file is $XDG_CONFIG_HOME/jcli/config.toml when XDG_CONFIG_HOME is set, non-empty and absolute, otherwise ~/.config/jcli/config.toml when HOME is absolute. There is no system-wide file. Unknown keys are an error.
  • A value that is present in a higher source wins even when it is blank or not valid Unicode. That setting then fails as configuration value <NAME> is set but empty; it never falls through to a lower source. Only an absent value falls through, and a setting absent everywhere fails as missing configuration value <NAME>.
  • Both files are read on every load, so an unreadable or malformed file fails the command even when the environment supplies every setting. File errors are generic and never show the file's contents.
  • A base URL only has to parse as a URL. jcli appends a trailing slash so API paths join onto any path prefix, and drops the query and fragment when it builds request URLs.

Following the trust model in AGENTS.md, jcli does not cap file sizes, check permissions or reject symlinks for these files (ADR 0003).

Jira and Xray requests

Jira

JiraClient sends only GET requests, with Basic authentication from JIRA_EMAIL and JIRA_API_TOKEN and the user agent jcli/<version> (ADR 0005). It keeps two reqwest clients:

  • The JSON client follows redirects only to the same scheme, host and port, for at most 9 redirects. A redirect to another origin is not followed, and the redirect status becomes a Jira API error.
  • The attachment client follows no redirects, so credentials never leave the configured origin. It asks Jira for redirect=false and accepts only status 200.

Both use a 10 second connect timeout and a 30 second request timeout. reqwest's blocking client applies the request timeout to sending the request and receiving the headers, then to each read on a streamed body. For attachments it is an idle timeout: a large video keeps downloading while data arrives.

CommandRequest
whoamiGET rest/api/3/myself
issue readGET rest/api/3/issue/{key}?fields=summary,issuetype,status,assignee,reporter,labels,created,description,attachment
issue searchGET rest/api/3/search/jql?jql=...&maxResults=N&fields=summary,status,issuetype,created,updated,labels
issue attachmentsGET rest/api/3/issue/{key}?fields=attachment, then GET rest/api/3/attachment/content/{id}?redirect=false per attachment
xray test-runsGET rest/api/3/issue/{key}?fields=summary for the numeric issue ID

jcli builds every URL from the configured base URL. It ignores the resource URLs in Jira's responses, and appends the issue key and attachment ID as single encoded path segments.

Issue, search and attachment metadata responses are read into memory up to 16 MiB; a larger body fails without truncation. whoami reads its small response without that limit.

Status codes map to fixed messages: 401 names JIRA_EMAIL and JIRA_API_TOKEN, 403 is a permission error, 404 names the resource, 429 asks to retry later, and anything else reports only the HTTP status. Error messages never contain response bodies, with one exception. A 400 from the search endpoint reads Jira's errorMessages and errors from a body of at most 64 KiB and joins them into one line: invalid JQL query (400): .... Each message is reduced to one terminal-safe line, and field errors with a blank message are dropped. The API token and the Basic authorization value, with and without the Basic prefix, become [REDACTED]. The email stays, because JQL errors quote it. Without a usable message the error falls back to the generic HTTP 400.

Xray

Xray Cloud authenticates and queries over POST, so XrayClient cannot be GET-only. It sends two requests per xray test-runs call, and neither changes Xray data:

  1. POST api/v2/authenticate with the client ID and secret. Xray answers with a bearer token as a bare JSON string, read up to 64 KiB. The token lives only for this call.
  2. POST api/v2/graphql with the bearer token and the getTestRuns query for the numeric issue ID. limit is 100 and start is 0. --status values travel as a GraphQL variable, never as query text. The response is read up to 16 MiB.

The Xray client follows no redirects, because both requests carry credentials. It uses the same 10 second connect and 30 second request timeouts. Status codes map like the Jira ones. A GraphQL errors array in a 200 response becomes the generic Xray GraphQL query failed; the server's message is discarded because it may echo input. reqwest errors have their URL removed before jcli stores them.

Output

Output is written for agents (ADR 0007). Results go to stdout as Markdown or JSON with no colors or progress. Errors go to stderr as one error: line once the arguments parse, and the exit code is non-zero. Invalid arguments get clap's multi-line usage message and exit 2.

issue read prints:

# ABC-123: <summary>

- Type: <issue type or Unknown>
- Status: <status>
- Assignee: <display name, Unassigned or Unknown>
- Reporter: <display name or Unknown>
- Created: <timestamp as Jira returns it, or Unknown>
- Labels: <comma-separated or None>
- Attachments: <count>

## Description

<ADF rendered as Markdown, or No description.>

Metadata values are reduced to one line, have control and bidirectional formatting characters removed and have Markdown characters escaped. The ADF renderer handles paragraphs, headings, bullet and ordered lists, code blocks, blockquotes, hard breaks and the strong, em, code and link marks. Links render only for absolute http and https URLs. For an unknown node it renders the text and known child content it can find instead of failing the issue. Comments are not rendered.

issue search prints pretty JSON with jql, returned, truncated and issues. truncated is !isLast, or null when Jira omits isLast. Each issue has key, issueType, status, summary, created, updated and labels. Missing values stay null, except labels, which becomes []. Issues keep Jira's order, so sorting is done with ORDER BY in the JQL. jcli passes the JQL to Jira unchanged and fetches only the first page; --limit defaults to 20 and accepts 1 to 100. An empty result exits 0 with "issues": [].

xray test-runs prints pretty JSON with testKey, total, returned, truncated, start, limit and runs. Each run has id, status, startedOn, finishedOn and testExecutionIssueId; a null entry from Xray stays null. truncated is total > returned, or null without a total. --sort started-on reorders only the returned page, newest first unless --direction asc is given. Runs with a missing or unparseable startedOn come after dated runs, and null entries come last. Ties break by run ID, then by original position.

Both JSON outputs escape DEL, the C1 control range and bidirectional formatting characters as \uXXXX, so parsing the JSON returns the original text.

issue attachments prints # <KEY> attachments followed by one - <file name> line per downloaded file, or No attachments. In the second case it creates no directory.

whoami prints <display name> <<email>> (<account ID>) with placeholders for missing values.

Attachment downloads

issue attachments writes into ./<KEY>/, or into the directory given with --out, which jcli uses as is. It plans every download before the first request and rejects the whole set when:

  • an attachment ID is empty, longer than 256 bytes, . or .., or repeated,
  • a size is negative or larger than 20 GiB,
  • the set has more than 1,000 attachments or more than 100 GiB in total,
  • two generated file names are equal when compared case-insensitively.

A file name is <id>-<filename>, at most 240 bytes. A numeric ID of up to 48 bytes stays as is; other IDs become id-<hex> or, when longer than 48 bytes, id-sha256-<hash>. The filename keeps ASCII letters, digits, . and -, and collapses every other run of characters to one -. Leading and trailing dots and hyphens are trimmed, an empty result becomes attachment, and Windows device names such as CON get a file- prefix.

jcli creates the output directory with mode 0700 when it is missing. It then downloads attachments one at a time in Jira's order. Each download streams into a temporary .jcli-attachment-* file in that directory, which only the owner can read. The byte count must match the size in Jira's metadata exactly. A verified file then atomically replaces its final name. If a later attachment fails, the files already replaced stay, the failed temporary file is removed and stdout stays empty (ADR 0009).

Credentials

Credentials never reach output. Config, XrayConfig and XrayClient implement Debug by hand and print only a URL without user info, query or fragment. Error messages name settings, not values. The only Jira text that reaches an error is the JQL error described above, with credentials redacted. Xray GraphQL messages are dropped.

Tests and quality gates

Unit tests live next to the code in #[cfg(test)] modules. They cover parsers, the ADF renderer per node type, configuration precedence through a testable from_sources function, download planning and file naming. Client tests use httpmock to check the exact requests, authentication headers, status mapping and body limits. Timeout tests start raw TcpListener servers that stall headers or bodies, or that keep sending data past the request timeout.

The CLI tests in tests/ are black-box tests. tests/common/mod.rs runs the built jcli binary with a cleared environment, in a fresh temporary directory or one the test provides. Each test starts its own httpmock server, and the tests assert only on stdout, stderr, exit codes and written files.

The gates (ADR 0004):

  • cargo fmt --check, also run by the .githooks/pre-commit hook.
  • cargo clippy --all-targets -- -D warnings. Cargo.toml also denies the whole clippy::all group.
  • cargo test.
  • cargo llvm-cov for coverage and cargo crap for the CRAP score, with the threshold in .cargo-crap.toml.
  • cargo machete for unused dependencies.
  • cargo mutants. Pull requests check the mutants in their diff against the base branch; pushes to main and manual runs check the full suite in four shards. .cargo/mutants.toml sets a minimum test timeout of 20 seconds for the timeout tests.

CI runs the gates in jobs; fmt and clippy share the Lint job. The ci-success job fails if any job failed or was cancelled, and a ruleset on main requires it.
